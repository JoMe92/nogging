# Nogging unter WSL auf Windows 10

**Ergebnis: geht mit Einschränkungen.** Nogging kann in Ubuntu unter WSL2 als Linux-Toolchain
installiert und interaktiv benutzt werden. WSL ist in Nogging 3.x jedoch ausdrücklich **nicht
unterstützt**; die Kombination hat keine Release- oder Abnahmeabdeckung. Windows 10 22H2 kann
WSL2 ausführen und mit aktueller WSL-Version auch systemd bereitstellen, aber der reguläre
Support für Windows 10 endete am 14. Oktober 2025. ESU und LTSC haben eigene Supportbedingungen.
Für die tägliche interaktive Entwicklung ist WSL2 plausibel; dauerhaft laufende Dienste und
Fernzugriff brauchen zusätzliche Prüfung.

## Funktionsübersicht

| Funktion | Einschätzung | Einordnung |
| --- | --- | --- |
| Nogging-Installation und interaktive Linux-CLI | **Mit Anpassung** | Ubuntu/WSL2 sieht sich als Linux. Der Linux-Installationspfad passt grundsätzlich. Nogging führt WSL aber als nicht unterstützte Plattform; `doctor` ist kein WSL-Kompatibilitätstest. |
| WSL1 | **Geht nicht** | Nicht verwenden: systemd fehlt; Claude-Code- und Codex-Sandbox benötigen WSL2 bzw. Linux-Namespaces. |
| Systemd, User-Units und Timer | **Mit Anpassung** | Auf WSL 2 mit WSL-Paket ≥ 0.67.6 aktivierbar. Nogging-Sync-Timer und User-Service können laufen, solange die Distribution läuft. Systemd-Dienste halten WSL selbst nicht am Leben. |
| tmux / herdr-Sitzungen | **Mit Anpassung** | tmux läuft im Linux-Gast. Sitzungen gehen verloren, wenn WSL herunterfährt; das optionale herdr-Backend ist nicht nötig. Der Orchestrator ist fest an tmux gebunden. |
| Dolt und `bd` | **Mit Anpassung** | Beide laufen als Linux-Programme in WSL. `doctor` prüft `bd` und `dolt` auf `PATH`; Beads muss dennoch mit dem vorgesehenen Dolt-Server verbunden sein. Läuft dieser auf Windows statt in WSL, ist unter dem Windows-10-NAT die Host-IP statt eines vorausgesetzten gemeinsamen `localhost` zu verwenden. |
| Dateien und Worktrees | **Geht** | Repo im WSL-ext4-Dateisystem anlegen, etwa `~/code`. Microsoft empfiehlt das für Linux-Tools; `/mnt/c` ist langsamer und kann Linux-Dateirechte/Dateisystemverhalten beeinträchtigen. |
| Claude-Code-Sandbox | **Mit Anpassung** | Claude Code unterstützt WSL2 und nutzt `bubblewrap` plus `socat`; Sandbox im Agenten prüfen. Sie schützt Shell-Kommandos, nicht Claude-Dateitools, MCP-Server oder Hooks. |
| Codex-Sandbox | **Mit Anpassung** | Codex nutzt unter WSL2 die Linux-Sandbox mit Bubblewrap; WSL1 wird nicht unterstützt. User-Namespaces müssen funktionieren. Codex verwendet zusätzlich seccomp; Landlock ist ein älterer Implementierungspfad. |
| Pi-Sandbox | **Geht nicht** | Nogging dokumentiert für Pi keine validierte Datei- oder Netzwerk-Sandbox. Die Nogging-Guard-Erweiterung ist eine Projektgrenze, kein Betriebssystem-Sandbox-Ersatz. |
| Remote Control des Orchestrators | **Mit Anpassung** | Remote Control ist eine Claude-Funktion und benötigt ausgehendes Internet. Es ist nicht an Tailscale gebunden. Der Orchestrator hängt zusätzlich an systemd-User-Service und tmux, die WSL nicht dauerhaft am Leben halten. |
| Dashboard lokal | **Geht** | Vordergrundserver auf Loopback; aus Windows kann WSL2-Loopback-Forwarding gewöhnlich über `localhost` erreicht werden. |
| Dashboard per Tailscale | **Mit Anpassung / ungeprüft** | Nogging bindet an eine private Adresse, für Tailscale typischerweise an eine `tailscale*`-Schnittstelle in WSL. Tailscale empfiehlt auf WSL2 grundsätzlich den Windows-Client allein; gleichzeitige Clients in Windows und WSL haben Einschränkungen. Das Zusammenspiel mit Nogging-Dashboard auf Windows 10 wurde nicht verifiziert. |
| Hintergrundbetrieb nach Abmelden/Neustart | **Geht nicht ohne Host-Startmechanismus** | `systemctl --user enable` und Linger ersetzen nicht den Start der WSL-Distribution. Windows muss WSL starten; WSL kann danach bei Inaktivität enden. |

## Einrichtung

1. **Windows und WSL prüfen.** In `winver` Windows 10 22H2 (Build 19045) prüfen. In einer
   administrativen PowerShell WSL aktualisieren und Ubuntu installieren bzw. starten:

   ```powershell
   wsl --update
   wsl --install -d Ubuntu
   wsl --list --verbose
   ```

   In der Ausgabe muss Ubuntu Version `2` verwenden. Falls nicht: `wsl --set-version Ubuntu 2`.
   WSL2 ist auf Windows 10 ab Version 1903 / Build 18362 verfügbar; ein aktuelles Store-WSL ist
   nötig für systemd. Falls `wsl --version` nicht erkannt wird, erst WSL aktualisieren. Windows
   10 22H2 ist die letzte allgemeine Windows-10-Version und hat das reguläre Supportende bereits
   erreicht.

2. **systemd für User-Units einschalten.** In Ubuntu `/etc/wsl.conf` ergänzen oder den
   vorhandenen Inhalt erhalten und den Abschnitt hinzufügen:

   ```ini
   [boot]
   systemd=true
   ```

   Dann aus PowerShell `wsl --shutdown`, Ubuntu neu öffnen und `systemctl status` prüfen. Für
   Debian/Ubuntu nennt Microsoft zusätzlich das Paket `systemd-sysv`, falls erforderlich.

3. **Projekt im Linux-Dateisystem halten.** In WSL `mkdir -p ~/code && cd ~/code`; den Git-
   Checkout dort anlegen. Nicht unter `/mnt/c/...` entwickeln, sofern es keinen konkreten
   Windows-seitigen Grund gibt.

4. **Linux-Toolchain installieren.** Für eine frische Ubuntu-Installation den in Noggings README
   genannten, auf einen Release-Tag gepinnten Bootstrap verwenden. Er richtet Node, OpenSpec,
   `bd`, Dolt, Git, tmux und GitHub CLI ein. `--with-pi` nur ergänzen, wenn Pi gebraucht wird.
   Bei bestehender Toolchain die gepinnte `npx ... init`-Installation verwenden. Danach
   `./scripts/nogg doctor` ausführen und jeden FAIL beheben. `doctor` prüft mindestens Git,
   Python, `bd` und Dolt auf `PATH`; Node/OpenSpec-Versionen erscheinen als Baseline, es ist
   aber kein WSL-Abnahmetest.

5. **Beads/Dolt-Verbindung sicherstellen.** Prüfen, dass `bd` dieselbe vorgesehene Beads-
   Datenbank erreicht. Bei einem Dolt-Server im WSL-Gast dessen Linux-Loopback verwenden. Bei
   einem Windows-Hostdienst die unter WSL sichtbare Windows-Host-IP und Firewall/Portfreigabe
   prüfen; Windows 10 hat keinen Mirrored-Modus, der die Netzwerkschnittstellen und `localhost`
   wie Windows 11 teilt.

6. **Agenten gezielt einrichten.** Claude Code in WSL installieren und `/sandbox` öffnen; auf
   Ubuntu fehlen bei Bedarf `bubblewrap` und `socat`. Für Codex in WSL Bubblewrap installieren
   und die Sandbox im tatsächlichen Profil prüfen. Nogging empfiehlt Pi nicht als isolierten
   Agenten, da dort keine OS-Sandbox validiert ist.

7. **Zunächst interaktiv arbeiten.** `doctor`, `validate`, Beads, Worktrees und Sessions in der
   laufenden WSL-Distribution ausprobieren. Sync-Timer oder Orchestrator erst danach optional
   mit den dokumentierten `systemctl --user`-Befehlen aktivieren. Diese Units starten WSL nicht
   selbst und garantieren keine dauerhafte Laufzeit.

8. **Dauerbetrieb separat planen.** WSL-Konfiguration unterscheidet sich nach installierter WSL-
   Version: die aktuelle Dokumentation nennt unter `[general]` `instanceIdleTimeout=-1`; für
   `[wsl2]` ist außerdem `vmIdleTimeout` dokumentiert. Diese Werte sind keine Boot-Automatik und
   garantieren keinen dauerhaften Betrieb. Ein Windows-Task/Hostdienst, der die Distribution
   startet, ist ein möglicher Ansatz, aber für Nogging, User-Linger und WSL-Idle nicht in diesem
   Repo oder durch diese Recherche abgenommen.

9. **Dashboard erst lokal prüfen.** Für lokale Nutzung `./scripts/nogg dashboard` auf Loopback
   starten. Fernzugriff über Tailscale erst konfigurieren, wenn in WSL die passende private
   Adresse und der Zugriff aus dem Tailnet tatsächlich getestet wurden. Tailscale dokumentiert
   WSL2 als fortgeschrittene Einrichtung und empfiehlt normalerweise, nur den Windows-Tailscale-
   Client zu betreiben.

## Repo-Befund

- README nennt Linux als Plattform; Windows und WSL sind nicht beansprucht.
  `docs/compatibility.md` führt Ubuntu x86_64 als unterstützt und WSL als **unsupported**, da
  Pfad-, Shell-, Service-Manager- und Sandbox-Verhalten nicht in Release-Gates abgedeckt sind.
- Die Installation braucht Debian/Ubuntu-Familie, Node.js, Python, Bash, Git, OpenSpec, Beads
  und Dolt. tmux ist optional, aber Standard für überwachte Sessions; systemd-User-Manager ist
  optional. `--no-systemd` erlaubt den interaktiven Betrieb ohne Timer.
- `scripts/nogg doctor` prüft auf Tool-Ebene Git, Python, den konfigurierten `bd`-Befehl und
  Dolt; außerdem Repo-Konfiguration/Validierung, optionale Agenten, Session-Backend, Dashboard-
  Sicherheit und optionale systemd-Units. Es gibt keine WSL-, Windows-Build-, WSL-Version-,
  Netzwerkmodus- oder Idle-Prüfung. Systemd/Orchestrator-Abwesenheit ist überwiegend NOTE statt
  FAIL.
- `bd` kommuniziert mit der Dolt-basierten Beads-Datenbank. In dieser Konfiguration ist der
  Dolt-Server ein eigener Hostdienst; ein `bd`, das in einem Agenten-Sandbox ohne Netzwerk
  läuft, erreicht ihn nicht. In WSL muss die Netzwerkroute zum Server stimmen.
- Die systemd-Sync- und Orchestrator-Units sind User-Units; der Orchestrator ist zusätzlich an
  tmux gebunden. Remote Control ist nur für den Claude-Orchestrator dokumentiert. Das optionale
  Dashboard kann loopback oder an einer erlaubten privaten Adresse lauschen; der Netzwerk-Bind
  wird auf die passende private Host-Schnittstelle beschränkt.

## Offene Punkte

- WSL ist offiziell nicht unterstützt: Für eine Support-Aussage braucht es einen vollständigen
  manuellen Abnahmelauf auf Windows 10 22H2 mit der konkreten WSL-/Ubuntu-Version.
- Welcher Windows-10-Build und welche WSL-Paketversion auf dem Ziel-PC installiert sind, ist
  nicht bekannt. Ebenfalls offen: Edition und möglicher ESU-/LTSC-Status.
- Nicht verifiziert sind `systemd --user`-Linger und User-Timer über Windows-Abmeldung/Neustart
  sowie eine robuste automatische WSL-Aktivierung für den Orchestrator.
- Nicht verifiziert ist, ob Tailscale nur auf Windows eine nutzbare `tailscale*`-Adresse für den
  Dashboard-Prozess in WSL2-NAT bereitstellt. Tailscale rät vom parallelen Windows- und WSL-
  Client ab.
- Sandbox-Funktion muss nach Installation in der konkreten Agenten-Version geprüft werden. Für
  Claude Code gilt außerdem, dass die Sandbox nicht Claude-Dateitools, MCP oder Hooks umfasst.
